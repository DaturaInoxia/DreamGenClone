## Notes

In session 44d9af9f-cc16-421c-b838-040e20b95305 (Campground Intimacy, Approaching, NTR Open World), many overflow-continue turns generate ONLY Dean (OtherMan) + Narrative — no Becky (Wife), no Ken — so Dean's seduction actions (tropes, e.g. helping/chopping-wood at the Husband and Wife Trailer) go entirely unnoticed by the Wife, defeating their purpose. The "Dean, Dean, Narrative" the user sees is two consecutive Dean-only overflow turns (each continue click re-selects only Dean), not one turn with Dean twice. **Root cause (verified, 4-step chain)**: (1) **Location text was removed from the prompt but NOT from the logic** — the presence gate `IsActorInScene` (TrueLocation == CurrentSceneLocation) still drives actor selection; (2) **the background LLM location-detection produced the WRONG scene location** — `CurrentSceneLocation` was "The Other Man's Trailer" (Evening, cacheKey `Approaching|The Other Man's Trailer — Private Ground-Level Space|Becky,Dean,Ken|Evening`) when the narrative reality and the later-corrected truth state (16:40:33) are everyone at "Husband and Wife Trailer" (Morning) where Dean is helping; (3) **only Dean matched the wrong location** → `inScene:true` (score 1500, affinity Required); Becky/Ken `inScene:false` (score 200); (4) **the LLM actor-selection excluded out-of-scene characters even though all 3 are "available"** (debug 009 2026-07-18 made no-affinity chars available via `_ => inScene` → `_ => true`, but the gate just moved to the LLM decision stage) — LLM stated reasoning: "Dean is the only in-scene character and is Required by affinity; Ken and Becky are marked as out-of-scene for this moment." (`Candidates=3, Ordered=1`); engine then computes `batchSize = min(SceneContinueBatchSize=3, sceneActors.Count=1) = 1`. NOT a seduction-archetype injection bug (confirmed working — Dean's prompt carries `Seduction style:`). **Three compounding defects**: (A) unreliable location detection set the wrong CurrentSceneLocation; (B) LLM actor-selection over-respects `inScene`, dropping out-of-scene chars from participation; (C) presence gate blocks line-of-sight characters — Becky had 100% line-of-sight + proximity (`CharacterLocationPerceptionsJson`) yet was `inScene:false`. **Fix options captured (2026-08-12)**: (1) **[SELECTED] Presence gate uses line-of-sight/proximity** — fix `RolePlayScenePresenceHelper.IsActorInScene` to consider `CharacterLocationPerceptionsJson` (HasLineOfSight/IsInProximity) instead of strict `TrueLocation == CurrentSceneLocation` exact match; Becky's perceptions showed 100% line-of-sight + proximity yet she was `inScene:false` — the system already knows she is watching but the gate ignores it. (2) **[SELECTED] LLM actor-selection treats out-of-scene as lower-priority, NOT disqualifying** — fix `ResolveSceneContinueActorsAsync` so the LLM receives out-of-scene chars as eligible-but-lower-priority, completing debug-009's unfinished fix (it made them available but the LLM still drops them, `Candidates=3, Ordered=1`). (3) **[NOT SELECTED] Presence expansion band-aid** — special-case singleton OtherMan in-scene → force-include Wife; too hacky, does not fix the underlying flaw. (4) **[NOT SELECTED] Location detection robustness** — fix the background LLM location-detection job; LLM parsing is inherently noisy, fights the symptom upstream. **Decision: implement options 1 + 2 together** (complementary + principled: Option 1 makes the presence gate respect observed line-of-sight so the Wife is in-scene when watching; Option 2 prevents the LLM from dropping eligible characters regardless of the gate — the natural completion of debug-009). Evidence: `OverflowActorSelection` debug events + LLM reasoning + cacheKey vs corrected truth state + `CharacterLocationPerceptionsJson` + debug note `specs/001-rp-prompt-redesign/debug/009-actor-availability-location-gate.md`. **Implementation (2026-08-12, options 1+2)**: Option 1 — `RolePlayScenePresenceHelper.IsActorInScene` now returns true on (a) TrueLocation==CurrentSceneLocation OR (b) line-of-sight/proximity (via `CharacterLocationPerceptions`) to any character authoritatively at the current scene (follows the `IsTransgressorInImmediateVicinityOfPartner` precedent). Option 2 — (a) `ActorSelectionService` system prompt now states `InScene: False` does NOT disqualify (out-of-scene observers remain eligible, lower-priority only) and not to narrow to one in-scene char; (b) new `RolePlayEngineService.GuaranteeParticipationSeats` post-guard guarantees eligible in-scene + Required-affinity candidates get a seat up to batch size, only ever ADDING to LLM choices, respecting Affinity-Excluded + ParticipateInAutoContinue=false. Tests: `RolePlayScenePresenceHelperTests.cs` (11) + `RolePlayParticipationGuardTests.cs` (8) — all pass; build clean (0 errors). Awaiting live verification on a real session. |
