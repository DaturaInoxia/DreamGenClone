# B-076: Staged Directions slot — one-shot batch queue injected on next continuation

**State**: ``implemented``
**Priority**: high
**Scope**: medium

---

## Notes

Every `+` submission always stages with `IsStagedDirection=true` (no toggle, no opt-in — replaces B-074 history-stage behavior for `+`). Add a new `IsStagedDirection` boolean flag on `RolePlayInteraction` (rather than a separate list/type) and a new `StagedDirectionsSlot` (`PromptSlotId.StagedDirections = 20`, `Zone = C`, `Order = 9` — renders after `PinnedContextSlot` Order 8) that injects all staged interaction rows as a single batch block on the **next** `…` continuation, then **graduates** the staged rows (sets `IsStagedDirection = false`) after the prompt is built but before the LLM call returns — one-shot guarantee even on failed continuation. Distinct from `PinnedContextSlot` (B-074: pinned = persistent; staged = one-shot, consumed on next `…`). Staged entries live in `session.Interactions` (NOT a separate list) with the flag — this unlocks ALL existing per-interaction commands (Retry / Rewrite / Expand / MakeLonger / MakeShorter / AskToRewrite / Pin / Exclude / Hide / Delete) on staged rows for free, including the user-requested "write a sentence + have LLM rewrite/expand it before consuming the batch" workflow. Composes with pinned: a pinned interaction (e.g. pinned "Ken cannot hear what is happening in the neighbor's trailer") renders FIRST at Order 8, then the staged one-shot plan (e.g. `Becky heads to shower` / `Ken turns on TV` / `Dean waits then follows Becky` / `Instruction: Becky leaves door open, Dean watches`) renders at Order 9 — persistent constraints precede the beat plan. `InteractionHistorySlot` filters `!IsStagedDirection` so staged rows don't double-count in `Interaction History`; after graduation (flag flips to false), they fall back into `Interaction History` as past context on the next turn. Persistence: staged rows are normal `RolePlayInteraction` rows — `IsStagedDirection` flows through the existing session JSON blob serializer (same path as `IsPinned`, `IsExcluded`, `IsHidden` flags) — user can stage entries, close the tab, come back later, and `LoadSessionAsync` rehydrates them with the staged badge intact; the next `…` consumes them as if never away (matches B-074 pinned reload behavior; dev.db-only, does NOT travel via git snapshot). UI: staged-mode toggle near prompt toolbar (default OFF — existing B-074 `+` history-stage behavior unchanged), staged rows render in the existing interaction list with a "STAGED" badge/tint, no separate queue preview chip (kebab menu already operates per-row).
